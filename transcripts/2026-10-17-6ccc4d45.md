🤖 **Claude**

Claude Code has a few **permission modes** that control how much I can do without asking you. Press **Shift+Tab** to cycle through them. The current mode is shown at the bottom of the prompt.

### Permission modes

| Mode | What it does | When to use it |
|---|---|---|
| **Default** | I ask before editing files or running shell commands, unless you've already allowed that action. Reading and searching don't need approval. | Unfamiliar code, or when you want to review each step |
| **Accept edits** | File edits are approved automatically. Shell commands and other riskier actions still ask first. | You trust the direction and don't want to approve every edit |
| **Plan mode** | Read-only. I can explore the code and write a plan, but I can't edit files or run commands that change anything. When the plan is ready, you approve it before I start. | Large or unclear tasks where you want to agree on the approach first |
| **Auto mode** | A separate classifier model checks each action before it runs. Routine, low-risk actions go through without a prompt. Risky ones get blocked or sent to you, such as deleting things, force-pushing, sending data outside your machine, or going beyond what you asked for. | Longer tasks where you want fewer interruptions but still want guardrails |
| **Bypass permissions** (`--dangerously-skip-permissions`) | No checks at all. Everything runs. | Only in throwaway sandboxes or containers |

**Auto mode is on in this session right now.** It sits between "approve everything yourself" and "approve nothing." Instead of a fixed allowlist, it judges each action in context, so the same command can be fine in one task and flagged in another. It's not a guarantee, so for sensitive repos or production credentials, default mode is safer.

### Other settings people sometimes call "modes"
- **Fast mode** (`/fast`): faster output from the same Opus model. It's about speed, not permissions.
- **Allow/deny rules**: in `settings.json` (or via `/permissions`) you can always allow or always block specific tools or commands, like `npm test`, in any mode.
- **Effort level**: controls how much I think before answering. Lower is faster, higher is more thorough.

A common pattern is to start a big feature in plan mode, agree on the plan, then switch to accept edits or auto mode to carry it out.

## Is Docker worth it just for skip-permissions?

**Probably not for you right now.** Here's why:

- **Auto mode already gives you most of the benefit.** You get far fewer prompts, and the risky actions still get caught.
- **The setup isn't free.** You'd install Docker or OrbStack, write a devcontainer config, sort out file mounts, and reinstall your tools inside the container. Things also get a bit slower and clunkier, especially file watching and GUI tools.
- **Bypass mostly pays off for long unattended runs.** That means kicking off a task and walking away for an hour, or running several agents at once. If you're at the keyboard watching anyway, the gain is small.

It becomes worth it if you start doing those long or parallel autonomous runs often. Even then, Claude Code on the web covers a lot of the same need without local setup.

## Using claude.ai/code

It runs Claude Code in a VM that Anthropic manages. How it works:

1. **Put your code on GitHub.** Web sessions clone from a GitHub repo. **This folder isn't a git repo yet**, so you'd need to `git init` and push it to GitHub first. Make the repo private if it's a take-home.
2. Go to **claude.ai/code** and install the **Claude GitHub app** on that repo.
3. **Set up an environment.** You choose how much network access the VM gets and add any environment variables. You can also add a setup script, e.g. `pip install -r requirements.txt`.
4. **Give it a task.** It works on its own in the VM and pushes to a branch, and you can open a PR from there. You can watch it, steer it while it runs, or close the tab and come back later.
5. **Pull it back to your laptop if you want.** Sessions can be moved into your local CLI ("teleport") so you can keep going locally.

**1. Paying for Claude Code itself.** This isn't done with an API key. Web sessions run on your **claude.ai subscription** (Pro, Max, Team or Enterprise). ## 1. Getting transcripts out of a cloud session

There's no download or export button for cloud sessions. Your options:

- **Teleport it to your laptop:** run `claude --teleport` (or `/teleport` inside the CLI). It checks out the session's branch and loads the full conversation into your terminal. You then have your own local copy, and new work there doesn't sync back to the cloud.
  - **Requirements:** a clean git state, a checkout of the same repo, the branch pushed to GitHub, and being logged in with your claude.ai account (not an API key).
- **Save it as text:** once it's loaded locally, `/export` saves a readable plain-text transcript.
- **Raw local files:** local sessions are saved as JSONL in `~/.claude/projects/<project-path>/<session-id>.jsonl` and kept for 30 days by default. The docs don't say whether teleporting writes one of these files, so I wouldn't rely on that.
- **Share a link:** the web UI can share a session by link, with visibility set to Private or Public on Pro/Max. That lets someone view it but doesn't give you a file.

## 2. Moving a local session to the cloud

**The CLI can't move a running session to the cloud.** The docs say directly that you can pull cloud sessions down but can't push a terminal session up. What exists instead:

- **`claude --cloud "task"`** starts a *new* cloud session for the current repo. Your local conversation doesn't come with it.
  - The VM clones from GitHub, so push your commits first.
  - With no GitHub remote, the CLI uploads a bundle of the repo instead. That bundle includes uncommitted changes to tracked files, but not new files you haven't added to git. `.env` and key files are left out.
- **`claude -p "message" --cloud <session-id>`** sends a follow-up message to a cloud session that's already running.
- **The Claude Desktop app** can send a local session to the cloud from its **Open in** menu. That's the only documented way to move an existing session.

**Docs' suggested way to carry context over:** plan locally, save the plan to a file in the repo, commit and push it, then run `claude --cloud "Execute the plan in docs/plan.md"`. Anything from your local conversation the cloud session needs has to go in the prompt or in a committed file.
